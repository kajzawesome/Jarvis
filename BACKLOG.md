## Done (2026-08-01 — multi-monitor hot-plug, down-tracker, desktop-links auto-sync)

- [x] **Dynamic multi-monitor support** — confirmed `screen.getAllDisplays()` already scaled to however many monitors are connected at launch (1, 2, 3+, never hardcoded), but there was no handling for a monitor plugged/unplugged while Jarvis was already running. `main.js` now listens for `display-added`/`display-removed`/`display-metrics-changed` and does a debounced (~1s) full teardown + rebuild of every window rather than patching one in place — screen index is derived from left-to-right sort order, so adding/removing a display can shift every other screen's index, and patching risked a silent index-mismatch (wrong saved layout on the wrong physical monitor). Fixed the user's live stuck weather tile immediately (found + reproduced it: 6 tiles were off-screen on monitor 1, 4 more on monitor 2, all from before this fix existed) and self-heals any future stale layout the same way. **First version also ran on every interactive drag/resize** (`grid.on('change')`) — user reported "some of the resizing isn't working, it thinks it's an error" almost immediately, because a resize that crossed the fold got silently deleted mid-edit with a removal toast, reading exactly like the earlier "ton of resize issues" over-eager-rejection bug from earlier this session. - [x] **Toast-before-jarvisToast-exists bug, caught during this work**: `window.jarvisToast` was defined near the bottom of `app.js`, but the very first `applyLayout()` call (page load) now runs `pruneOffscreenItems()`, which could fire *before* that assignment ran — silently swallowing the very first toast. Moved the toast function/assignment to the top of the file, before node discovery/grid setup.
- [x] **Pause all node refresh timers while a screen is hidden/minimized** — Electron only stops rendering a hidden window, not its JS; every node's `setInterval` (including ones that shell out to PowerShell/WMI/docker/nvidia-smi on every refresh) kept running at full speed in the background. Not new to this session's performance work specifically, but the user is likely leaving Jarvis running uninterrupted for longer now that it isn't lagging their PC, so they're hitting it for the first time.

Verified live via a real `GetWindowRect` call (Win32, from PowerShell) against the actual running window: its real bottom edge now sits at ~1400px on a 1440px-tall display, matching the work area boundary (1392px + the usual few px of invisible DWM border on a frameless window) almost exactly - Windows is keeping the taskbar's strip clear on its own now that this isn't an exclusive-fullscreen surface. Taskbar should be directly clickable without `Ctrl+Alt+J` first.
- This was also the same underlying mechanism behind the earlier `window.prompt()`-renders-behind-the-window bug (native dialogs get suppressed by exclusive fullscreen the same way the taskbar does) - removing `fullscreen: true` likely would have fixed that too, though `window.jarvisPrompt` (the in-DOM replacement built for it) stays regardless, since it's a better pattern than native dialogs anyway.
